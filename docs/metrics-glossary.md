# 指标名词表（Metrics Glossary）

> 本文解释 [实测结果](./results.md)、[调研报告](./research.md)、[测试方案](./test-plan.md) 里出现的专业指标：**怎么算、怎么读、什么情况下会误读**。
> 所有示例数字都取自本项目的真实运行结果，可在 `reports/` 与 `outputs/` 中核对。

## 0. 一张表看懂

| 指标 | 一句话含义 | 方向 | 本项目示例 |
|---|---|---|---|
| **CER** | 字符错误率：改几个字符才能变成正确答案 | 越低越好 | OCR 2.50%，ASR 7.25% |
| **SWER / BoTok-SWER** | 分词后按"词"算的错误率 | 越低越好 | whisper-small 18.43% |
| **WER** | 词错误率（西文常用，藏文需先分词） | 越低越好 | 论文表格里与 CER 并列 |
| **SER** | 句错误率：整句有任何错误就算错 | 越低越好 | Yigdzin 官方 clean mean SER 7.64% |
| **灾难页率** | 单页 CER > 50% 的页面占比 | 越低越好 | Yigdzin 0%，Tesseract 53.3% |
| **覆盖率 coverage** | 模型实际输出结果的样本比例 | 越高越好 | 全部 100%（未缺失） |
| **mean / median** | 平均值 / 中位数，前者被极端值拉高 | - | 2.50% / 1.01% |
| **p10 / p90** | 分位数，描述分布尾部 | - | 榜单 p90 = 6.94% |
| **RTF** | 实时率：处理耗时 ÷ 音频时长 | 越低越好 | 0.023（43 倍实时） |
| **峰值内存** | 推理过程的内存占用上限 | 越低越好 | 1.3–1.8GB |
| **pp** | 百分点（percentage point），两个百分数直接相减 | - | 与论文差 0.2–4pp |

## 1. 所有指标的前提：参考与规范化

### 1.1 reference（参考）与 hypothesis（假设）

- **reference / ref**：人工标注的标准答案（ground truth）。
- **hypothesis / hyp**：模型的输出。

所有错误率都是"把 hyp 改成 ref 需要多少操作"。代码中对应 `scripts/common.py` 的 `cer(hyp_raw, ref_prepared)`。

### 1.2 Levenshtein（编辑）距离

把字符串 A 变成字符串 B 所需的最少**单字符操作**次数，允许三种操作：

| 操作 | 例子（藏文） | 代价 |
|---|---|---|
| 删除 | `བདེ་ལེགས` → `བདེ་ལེག` | 1 |
| 插入 | `བདེ་ལེག` → `བདེ་ལེགས` | 1 |
| 替换 | `འཇིཌ` → `འཇིགས` | 1（严格意义上是 2 次，见下） |

本项目用 `rapidfuzz.distance.Levenshtein` 计算，与 BDRC 官方打分脚本一致。

### 1.3 规范化（normalization）——为什么必须先做

原始文本直接比较会引入大量**与识别能力无关的差异**，例如空格数量、Unicode 组合方式不同但字形相同、tsheg（音节分隔符 `་`，U+0F0B）重复等。因此两边都要先规范化：

| 步骤 | 做了什么 | 目的 |
|---|---|---|
| botok `normalize_unicode` | Unicode 规范化（组合/预组合形式统一） | 同一字形不同编码不算错 |
| botok `normalize_graphical` | 字形层面的宽松归一 | 兼容历史编码差异 |
| `normalize_spaces` | 统一各类空白 | 空格不是藏文语义 |
| 去掉所有空白 `"".join(text.split())` | 移除空格/换行 | 榜单口径（OCR 的换行不影响内容） |
| 折叠连续 tsheg `U+0F0B{2,}` → `U+0F0B` | `་་་` 变 `་` | 连写多个分隔符是排版噪声 |
| 去掉占位符 `K O B I S` | 去除不可辨认/破损/涂改标记 | 这些是标注约定，不是待识别内容 |

> ⚠️ 规范化是**评测的一部分**。换了规范化规则，CER 会变（常见差 1–3pp）。所以跨报告比较数字时，必须确认口径一致——本项目严格复用 BDRC 官方 `compute_cer.py` 的规则。

## 2. 准确率指标

### 2.1 CER（Character Error Rate，字符错误率）

```
CER = Levenshtein(hyp, ref) / len(ref)
```

- 分母是**参考文本的字符数**（不是预测长度，避免"少说话就少犯错"）。
- 本项目按 BDRC 协议**单条封顶 1.0**：`min(distance/len(ref), 1.0)`。

**封顶为什么重要**：模型偶尔会输出病态结果（重复循环、整段乱码），编辑距离可能是参考长度的 5 倍。不封顶的话，一页坏页就能把 60 页的平均值拉爆；封顶后"最坏 = 全错 = 100%"，均值才有可比性。

**长度稀释效应**：CER 是"错误数 ÷ 字符数"，同样的 10 个错误，在 300 字短文里是 3.3%，在 1300 字长文里只有 0.77%。所以：
- 比较不同系统时，样本长度分布必须一致；
- 长文档的 CER 天然偏低，不能直接和短句 CER 比；
- 本项目的 `0764` 页（1302 字）CER 32.2%，是"1300 字里错了约 420 个字符"级别的问题，不是小瑕疵。

**本项目示例**：

| 场景 | ref 字符数 | 编辑距离 | CER |
|---|---:|---:|---:|
| 一个 55 字符的 ASR 句子，错 2 个字符 | 55 | 2 | 3.64% |
| 一个 17 字符的短句，丢了句末 shad `།` | 17 | 1 | 5.88% |
| 60 页 OCR 的页面级均值 | - | - | **2.50%** |
| 300 条 ASR 的句子级均值 | - | - | **7.25%** |

### 2.2 WER（Word Error Rate，词错误率）

```
WER = Levenshtein(hyp_words, ref_words) / len(ref_words)
```

把"字符"换成"词"。西文按空格切词即可；**藏文没有词间空格**（只有音节分隔符 tsheg），所以必须先分词，这就是 BoTok-SWER 存在的原因。

### 2.3 SWER / BoTok-SWER（Segmented WER，分词后词错误率）

```
SWER = Levenshtein(hyp_boTok_words, ref_boTok_words) / len(ref_boTok_words)
```

- 用 **botok** 对两侧分别分词，得到词序列，再算编辑距离。
- 词错误率对**语义**更敏感：藏文一个词常由 2–4 个音节组成，错一个字符往往整词报废。

**为什么 SWER 远高于 CER（本项目最容易被误读的一点）**

NICT-Tib1 参考文本实测：平均每个 botok 词 **4.57 个字符**、每句 **26 个词**。于是：

```
SWER ≈ CER × 平均词长 ≈ 7.25% × 4.57 ≈ 33%      （实测 28.56%）
```

直觉：错 1 个字符 → CER 只加 1/N_chars，但很可能让 1 个完整词变错 → SWER 加 1/N_words，而 N_chars ≈ 4.57 × N_words。

**一个具体例子**（本项目 `scripts/common.py` 实测）：

| | 参考 | 预测 |
|---|---|---|
| 文本 | `བཀྲ་ཤིས་བདེ་ལེགས། ང་ཚོས་བོད་ཡིག་སློབ་སྦྱོང་བྱེད་ཀྱི་ཡོད།` | `བཀྲ་ཤིས་བདེ་ལེག ང་ཚོས་བོད་ཡིག་སློབ་སྦྱོང་བྱེད་ཀྱི་ཡོད།` |

只丢了 1 个字符，结果：

- **CER = 3.64%**（1 / 55 字符）
- **SWER = 22.22%**（9 个词里 2 个出错）

同一份输出，"字符级看起来几乎完美"，"词级却错了 1/5"。所以报告藏语 ASR 时**必须两个都给**——这也是论文（IEEE Access 2026）的核心论点。

**怎么选**：

| 关注点 | 看哪个 |
|---|---|
| 检索/对齐/字符级校对成本 | CER |
| 可读性、下游 NLP（分词/翻译） | SWER |
| 编辑器里人工修正的工作量 | CER（改的是字符） |

### 2.4 SER（Sentence Error Rate，句错误率）

一条句子只要有 **任何** 字符错误就算错：

```
SER = 出错的句子数 / 总句子数
```

Yigdzin 模型卡给的 "clean mean SER 7.64%" 就是这个含义。它对"几乎全对但小错很多"的模型很苛刻，适合衡量"能不能直接交付、不用人工过一遍"。

### 2.5 灾难页 / 灾难率（catastrophic rate）

**定义**：单页（或单句）CER > **50%** 的样本占比。BDRC 榜单与本项目都用 0.5 作为阈值。

**为什么单独统计**：OCR 的失败不是均匀分布的，而是"绝大多数页面近乎完美 + 少数页面整页崩掉"。只看均值会掩盖这种双峰分布：

| 系统 | mean CER | median CER | 灾难页 | 解读 |
|---|---:|---:|---:|---|
| Yigdzin | 2.50% | 1.01% | 0% | 稳定可用，没有"整页报废" |
| Tesseract bod | 53.52% | 56.06% | 53.3% | 一半以上的页面基本不可用 |

生产上，灾难页意味着**必须有人工兜底流程**；灾难率为 0 才谈得上"批量自动处理"。

### 2.6 覆盖率（coverage）

模型对多少个样本**实际产出了结果**。当模型拒答、崩溃或超时，该样本按"全错"计入均值（BDRC 协议：缺失页 = CER 1.0）。

本项目所有 run 覆盖率 100%（`run.json` 中 `errors: 0`），因此均值没有额外惩罚；但如果对比榜单上的 Dots MOCR（398/472）、Transkribus（259/472），它们的 mean CER 里包含了大量"未尝试"的惩罚项，**不能只看 mean 就下结论**。

## 3. 汇总统计方式

### 3.1 mean 与 median

| | 定义 | 特点 | 本项目 OCR |
|---|---|---|---|
| **mean（算术平均）** | 所有样本相加 ÷ 样本数 | 被极端值拉高 | 2.50% |
| **median（中位数）** | 排序后正中间的那个值 | 抗极端值，代表"典型样本" | 1.01% |

两者差距大 = 分布有长尾。本项目 mean 2.50% vs median 1.01%，说明多数页面 CER <1%，少数页面（打字机、长手稿）拉高了均值。

**读法**：mean 对应"总体错误量/成本"，median 对应"随手抽一页的体验"。BDRC 榜单排名用 mean（更保守），同时列出 median 与 p90 供参考。

### 3.2 分位数（percentile）

榜单给出的 p10 / p25 / p75 / p90 表示"CER 低于该值的页面占比"：

| 分位 | Yigdzin（472 页榜单） | 含义 |
|---|---:|---|
| p10 | 0.00% | 最好的 10% 页面完全正确 |
| p25 | 0.24% | 1/4 页面几乎完美 |
| median (p50) | 0.96% | 典型页面 |
| p75 | 3.00% | 3/4 页面优于这个值 |
| p90 | 6.94% | 尾部：仍有 10% 页面 >6.94% |
| mean | 3.21% | 被尾部拉高 |
| max | 100% | 最差页面完全错误 |

只报均值会漏掉尾部风险；p90 才是"批处理时要预留多少人工复核"的依据。

### 3.3 分层抽样（stratified sampling）

按已知的重要维度（这里是"页面制作技术"与"文字类型"）按比例/配额抽取，而不是纯随机抽。目的：

1. 保证稀有类别（打字机仅 5 页、金属活字 17 页）也被测到，否则纯随机很可能抽不到；
2. 让不同系统的测试集完全一致，可做配对比较；
3. 报告时可按层拆开，定位"在哪种材料上失效"。

本项目 60 页 = 手稿 18 + 数字字体 14 + 木刻 14 + 现代 5 + 金属活字 5 + 打字机 4，层内兼顾 Uchen/Ume，随机种子固定为 42（`data/ocr/sample_ids.json` 可复现）。

### 3.4 分桶报告（per-bucket breakdown）

同一个模型在不同子集上差异可能极大，所以结果表按桶拆开：

- **per-technology**（数字字体 0.61% ↔ 打字机 12.77%）：反映材料难度。
- **per-script**（Uchen 2.7% / Ume 1.8% / 过渡体 0.8% / 混排 7.3%）：反映字体体系难度；混排最差，因为模型需要在同一页切换两种字形。
- **per-domain**（OpenPecha：有声书 6.8% ↔ 儿童语音 33.7%）：反映录音条件与说话风格。

结论层面的价值：**要判断一个模型"能不能用"，必须看与自己数据最接近的那个桶，而不是总均值。**

### 3.5 三种"不可比"的情况（最容易踩的坑）

| 场景 | 本项目中的例子 | 为什么不可比 |
|---|---|---|
| 不同样本量 | 60 页样本 vs 榜单 472 页 | 子集构成不同（榜单含 209 页手稿），且榜单对缺失页罚 1.0 |
| 不同抽样 | NICT 300 条 vs 全量 1,547 条 | 说话人/长度分布不同 |
| 不同子集筛选 | whisper-small 全部 300 条 8.31% vs ≤150 字 245 条 4.82% | 后者主动剔除了会被截断的长句——这是"诊断用"，不是"成绩" |

因此本项目所有对比表都**统一到同一子集**（`scripts/summarize_asr.py` 把全量 run 过滤到同一 300 条），并在正文标注口径。

## 4. 效率指标

### 4.1 RTF（Real-Time Factor，实时率）

```
RTF = 推理耗时 / 音频时长
```

- RTF = 1 表示"处理 1 分钟音频要 1 分钟"（刚好实时）。
- RTF < 1 才是可用的实时/离线批量方案；倍数 = 1 / RTF。

| 模型 | RTF | 实时倍数 | 含义 |
|---|---:|---:|---|
| wav2vec2-base | 0.023 | **43×** | 1 小时音频约 1.4 分钟处理完 |
| openpecha-general | 0.049 | 20× | 1 小时约 3 分钟 |
| whisper-small | 0.653 | 1.5× | 1 小时约 39 分钟，勉强实时 |

注意 RTF 受**硬件、批大小、音频长度分布**影响，只在本机横向比较有意义。

### 4.2 单页耗时（mean / median seconds per page）

OCR 是"一页一次前向"，没有音频时长可归一，所以直接报秒/页，并同时给中位数（避免被个别超长页拉偏）。

- 本项目：mean 36.4s / median 33.3s / max 114.7s（1,920 字符的超长页）。
- 耗时与**输出字符数**近似线性（自回归解码每 token 一次前向），所以长页慢是正常的。

### 4.3 峰值内存（peak memory）

推理过程中的内存/显存占用上限，两个来源：

- MPS 侧：`torch.mps.driver_allocated_memory()`（GPU 显存）
- CPU 侧：`ru_maxrss`（进程常驻内存峰值）

本项目：OCR（Yigdzin）约 **2.9GB**（视觉编码器要处理整页图），ASR **1.3–1.8GB**。它的意义是**能不能部署**：16GB 统一内存的 M4 上，3GB 级别意味着可以同时跑 OCR 和 ASR 而不至于触发内存换页。

### 4.4 吞吐（throughput）与延迟（latency）的区别

- **延迟**：单个请求多久返回（用户等待感）。
- **吞吐**：单位时间内能处理多少（批处理成本）。

本项目全部 batch=1（MPS 上批量解码易触发内存问题），报的是**延迟**；生产批量场景下吞吐可以靠批处理显著提升，但延迟会变差。

## 5. 模型与解码术语（结果表与工程要点里出现）

### 5.1 参数量的 B / M

`0.8B` = 8 亿参数，`94M` = 9,400 万。参数越多通常越准但越慢越占内存。本项目：Yigdzin 0.8B、whisper-small 244M、wav2vec2-base 94M、whisper-tiny 39M。

### 5.2 token / BPE / byte-level / 448 上限

- **token**：模型处理的最小单位，不等于字符也不等于词。
- **BPE（Byte-Pair Encoding）**：把高频字节对合并成 token 的压缩式词表。
- **byte-level**：先把文本拆成 UTF-8 字节再合并。藏文字符是 3 字节，所以**一个藏文字符通常占 ≈3 个 token**（本项目实测 3.03）。
- **448（`max_target_positions`）**：Whisper 解码器最多 448 个位置（含 4 个起始 token）。

由此推出本项目的关键结论：

```
最大可输出字符 ≈ (448 - 4) / 3.03 ≈ 145
```

这就是"whisper 会截断长句"的原因，也是要单独报告 **≤150 字子集** 的原因——它衡量的是"没有截断干扰时的真实精度"。

- **截断（truncation）**：输出在预算用尽时被强行截断，缺失的后半段全部算错，CER 随句子长度急剧上升。

### 5.3 解码策略

| 术语 | 含义 | 本项目设置 |
|---|---|---|
| **greedy（贪婪解码）** | 每步取概率最高的 token，最快最确定 | OCR、CTC 默认 |
| **beam search（束搜索）** | 同时保留 k 条候选路径，取整体概率最高 | `--beams 5` 可选；pilot 上仅从 43.1%→42.5% CER，收益很小 |
| **CTC + argmax** | 连接时序分类：逐帧输出字符再合并重复/空白，天然不受固定输出长度限制 | wav2vec2 / hubert |
| **自回归（autoregressive）** | 逐 token 生成，每个 token 一次前向 | Whisper、Yigdzin |

**重要区别**：CTC 输出长度由音频帧数决定，**没有 448 上限**；自回归模型的输出长度受解码预算约束。这解释了为什么 NICT 上 wav2vec2 的长句表现更稳。

### 5.4 KV cache / `use_cache`

自回归解码时，把已生成 token 的注意力 Key/Value 缓存起来，避免每步重算整个前缀。

- `use_cache=False`：每生成一个 token 都重算前面所有 token → 复杂度 O(n²)，**极慢**。
- `use_cache=True`：复杂度近似 O(n)（每步只算新 token）。

本项目实测：Yigdzin 生成 120 token 从 **83.4s → 7.5s**（约 11×），且输出**逐字节一致**（`cache=True/False` 前缀完全相同）。仓库自带 `generation_config.use_cache=false`，所以必须显式开启。

### 5.5 `mm_token_type_ids` / M-RoPE / sequential vs grid

- **M-RoPE（多模态旋转位置编码）**：图像 token 的位置编码方式，可按"网格二维坐标"或"一维顺序"计算。
- **grid（网格）**：按图像的行列 (h, w) 给位置，适合自然图像理解。
- **sequential（顺序）**：图像 token 按阅读顺序排成一条一维序列，更适合**整页文档**（保持行序）。
- **`mm_token_type_ids`**：标记每个 token 属于哪种模态（文本/图像）。Yigdzin 训练时用 sequential 方案，推理时必须把该标记清零，否则结构化页面会**漏行/串行**（官方称 CER 可从 ~10% 恶化到 ~62%）。

### 5.6 DRY（Don't Repeat Yourself）抗重复惩罚

自回归模型偶发"复读机"——反复输出同一段文本直到预算耗尽，整页报废。DRY 的做法：如果继续生成会让某个 n-gram 重复，就按重复长度**指数级压低**这些 token 的分数：

```
logits[t] -= multiplier × base^(L - allowed_length)     # 仅当 L ≥ allowed_length
```

| 参数 | 本项目取值 | 含义 |
|---|---:|---|
| `multiplier` | 0.8 | 惩罚强度系数 |
| `base` | 1.75 | 指数增长的底数（重复越长罚得越狠） |
| `allowed_length` | 12 | 允许重复的最大 n-gram 长度；短于它的自然重复（如咒语）不受罚 |

与 `repetition_penalty` / `no_repeat_ngram_size` 的区别：后两者是"硬规则"，会把合法的重复经文（mantra）也改掉；DRY 是按重复长度**渐进**惩罚，损伤小。本项目 60 页全部使用 DRY，灾难页 0。

### 5.7 数值精度与后端

| 术语 | 含义 | 本项目 |
|---|---|---|
| **fp32 / fp16 / bf16** | 浮点位数：32/16 位；bf16 与 fp16 同为 16 位但 bf16 指数位更多、动态范围更大 | OCR 用 bf16，ASR 用 fp16 |
| **MPS** | Apple Metal Performance Shaders，PyTorch 的 Apple GPU 后端 | 全部推理走 MPS |
| **SDPA** | PyTorch 的高效注意力实现（scaled dot-product attention） | `attn_implementation="sdpa"` |
| **量化（4bit/8bit）** | 用低位宽存权重以省内存，代价是精度 | 本项目未使用（论文中 LoRA/QLoRA 版本 CER 明显变差，如 68.4%） |

## 6. 数据与评测设计术语

### 6.1 说话人无关（speaker-disjoint）

测试集的说话人**完全不出现在训练集**。这是 ASR 可信度的底线——否则模型只是"记住了这个人的声音"。NICT-Tib1 的 test 是 3 位训练集未出现的说话人；本项目 300 条样本按说话人各抽 100 条，避免某一位说话人主导结果。

### 6.2 域内（in-domain）与域外（out-of-domain）

- **域内**：测试数据与训练数据分布一致（如 NICT 微调模型测 NICT）。
- **域外**：分布不同（如 NICT 模型测电影/儿童语音）。

本项目最有力的证据：

| 模型 | NICT（域内） | OpenPecha（域外） | 变化 |
|---|---:|---:|---:|
| wav2vec2-base | 7.25% | 54.02% | ×7.5 |
| whisper-small | 8.31% | 56.21% | ×6.8 |
| openpecha-general | 7.78% | 15.46% | ×2.0 |

**结论**：域内排名不能直接推广到生产；必须先确认业务音频属于哪个域。

### 6.3 数据泄漏 / 重叠（data leakage / overlap）

测试集内容（或其近似副本）出现在训练集里，导致指标虚高。本项目对 `openpecha/general_stt_base_model` 在 OpenPecha 基准上的 15.46% 标注了"可能重叠、视为乐观上界"，原因就是两者同源。

榜单侧同样处理：Yigdzin 训练时用 `images_exclude_from_train.csv` 把 472 页基准排除在训练之外。

### 6.4 pp（percentage point，百分点）

两个百分数相减的单位。7.45% → 7.25% 是"下降 0.2pp"（不是"下降 0.2%"）。本项目"与论文差距 0.2–4pp"就是这个用法。

### 6.5 藏文文字学术语

| 术语 | 含义 |
|---|---|
| **Uchen（དབུ་ཅན，有头体）** | 印刷体主流字体，笔画有"头" |
| **Ume（དབུ་མེད，无头体）** | 手写/草写体系，无"头"，连笔多，识别更难 |

## 7. 读表避坑清单

1. **先看口径**：规范化规则、是否有覆盖率惩罚、是否封顶——三者不同，数字不可直接比。
2. **别只看 mean**：配合 median、p90、灾难页率一起看，否则会把长尾风险藏起来。
3. **别跨子集比**：60 页 ≠ 472 页，300 条 ≠ 1,547 条，≤150 字子集 ≠ 全量。
4. **藏语要看两个指标**：CER 会系统性低估错误，SWER 更贴近语义；两者差 3–4 倍是正常的。
5. **RTF 只在本机内比**：换硬件、换批大小就不成立。
6. **域内成绩 ≠ 生产成绩**：先确认业务数据的域，再看对应桶的数字。
7. **注意许可**：非商用许可的模型即使精度最高也不能直接上线。
